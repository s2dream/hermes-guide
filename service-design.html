Hermes 가이드 / 서비스 설계

정보 탐색 에이전트를
여러 사람이 쓰는 서비스로.

Hermes의 탐색 능력에 자체 UI, 사용자 권한, 작업 관리와 근거 검증을 더합니다. 무엇을 요구사항으로 정하고 어떤 순서로 구현할지 정리한 설계 제안입니다.

요구사항·완료 기준권장 아키텍처개발·출시 순서

설계 초안 · 공개 웹 탐색부터 시작하는 제안 · 실제 서비스와 API는 아직 구현되지 않았습니다.

이 페이지에서

목표·초기 가정요구사항·완료 기준사용자 흐름·UI권장 아키텍처사용자 격리탐색·근거 품질도구·네트워크서비스 API작업·장애 복구데이터·보존운영·비용·성능개발·출시 순서요구사항 템플릿공식 근거

설치·연결을 마친 뒤, 제품으로 운영하기 위한 설계입니다. 가정과 확정 사항을 구분해 읽어 주세요.

무엇을 만들 것인가

우리가 만든 서비스 UI에서 여러 사용자가 질문을 등록하고, Hermes가 공개 자료를 찾아 근거가 연결된 조사 결과를 돌려주는 서비스를 목표로 합니다. 검색창뿐 아니라 사용자별 조사 이력, 작업 중단, 사용량 관리까지 하나의 제품으로 설계합니다.

이 페이지의 범위

이 문서는 요구사항과 구현 방향을 정리한 설계 제안입니다. 현재 GitHub Pages는 가이드이며, 아래의 로그인·조사 API·실행 워커가 구현되거나 운영 중이라는 뜻은 아닙니다.

초기안은 초대된 사용자에게 공개 웹 자료를 조사해 주는 서비스입니다. 조직을 구분하는 tenant와 그 안의 사용자·워크스페이스를 두되, 초기 결과는 개인 전용으로 보관합니다. 내부 문서 연결·공유 링크·정기 조사는 다음 단계에서 확장합니다.

구현 전에 합의할 결정
결정 항목초기 제안확인이 필요한 내용
서비스 대상초대된 사용자부터 시작사내 구성원인지, 외부 고객인지, 공개 가입까지 필요한지

사용 규모파일럿 10명, 전체 동시 작업 3개가입자 수와 별도로 최대 동시 조사·피크 시간 확인

위 수치는 논의를 시작하기 위한 가정이며 Hermes의 처리 성능이나 실제 사용자 요구를 측정한 값이 아닙니다. 대상·데이터·동시 사용량을 확정한 뒤 조정하세요.

사용자 요구사항과 완료 기준

P0는 첫 파일럿에 필요한 기능, P1은 파일럿 이후 확장할 기능입니다. 요구사항마다 실제로 통과 여부를 확인할 조건을 붙입니다.

기능 요구사항 초안
ID·우선순위사용자가 할 수 있어야 하는 일완료 기준
F01 · P0로그인하고 자기 공간 사용초대·로그인·로그아웃·계정 비활성화 동작. 인증된 사용자만 조사 생성 가능
F02 · P0조사 목적과 범위 지정질문, 목적, 기간, 허용 출처, 결과 형식을 입력·검증. 모호한 요청에는 추가 질문
F03 · P0대기·진행·종료 상태 확인대기·검색·원문 확인·정리 단계를 표시. 새로고침 후 같은 작업에 다시 연결
F04 · P0답변의 근거 확인핵심 주장에 실제 확인한 출처 연결. 원문 제목·URL·발행일(미상이면 미상)·조회 시각 제공
F05 · P0자기 조사 이력 재열람목록·본문·이벤트·출처·다운로드 모두 소유권 검사. 다른 사용자 ID로 바꿔도 접근 거부
F06 · P0조사 중단과 실패 확인중단 요청 후 실제 실행이 멈출 때까지 “중단 중” 표시. 실패와 근거 부족을 구분
F07 · P0한도와 사용량 이해조사 전 적용 한도 안내, 실행 후 실제·추정 비용 구분. 관리자는 계정별·전체 한도 조정
F08 · P1허용된 사내 문서 검색문서별 접근 권한을 검색 전·캐시 사용 시·결과 제공 시 검사. 권한 철회도 반영
F09 · P1팀과 결과 공유공유 범위·만료·회수 가능. 원문 접근 권한 없는 상대에게 근거 본문이 노출되지 않음
F10 · P1후속 조사·보고서 내보내기수정한 조건과 이전 결과의 관계를 보존. 내보내기도 본문과 동일한 권한·출처 적용
관리자 기능도 별도로 정의하세요.

계정·작업 수·실패율·비용·워커 상태는 운영 화면에서 확인합니다. 관리자가 모든 사용자의 원문·대화를 기본으로 열람하게 만들지 말고, 필요한 열람 권한과 감사 기록을 명시합니다.

사용 흐름과 자체 UI

  1. 사용자가 조사 질문·목적·기간·출처 범위를 입력합니다. 필요한 조건이 빠졌다면 먼저 보완합니다.
  2. 적용 한도를 확인하고 조사를 시작합니다. 대기열에 있으면 대기 상태를 보여 줍니다.
  3. 진행 중에는 조사 단계와 확인한 자료를 보여 주고, 언제든 중단 요청을 할 수 있게 합니다.
  4. 결과를 요약 → 근거가 붙은 핵심 내용 → 출처 목록 → 확인하지 못한 점 순서로 제공합니다.
  5. 자기 이력에서 다시 열거나 후속 질문을 합니다. 공유와 문서 업로드는 권한 설계 후 추가합니다.

UI에는 작업 단계와 출처 확인 상태를 보여 주되 모델의 내부 추론이나 원시 도구 인자·서버 경로를 그대로 내보내지 않습니다. 자료를 못 찾은 경우에는 빈 결과와 재조사 방법을 제시합니다. 기존 웹 UI 연동 가이드는 빠른 검증용으로 활용하고, 제품 UI의 회원·권한·이력 정책은 직접 설계합니다.

권장 시스템 구조

권장 시작점은 자체 UI → 서비스 API → 작업 관리자 → 사용자별 Hermes 실행 환경입니다. UI는 서비스를 호출하고, 서비스만 내부의 Hermes에 접근합니다. 역할을 분리하면 제품의 로그인·이력 정책과 Hermes 버전 변경을 각각 관리할 수 있습니다.

구성 요소별 책임
구성 요소직접 만들거나 운영할 부분Hermes와의 경계
서비스 UI질문 입력·진행·결과·출처·이력·접근성Hermes API 키와 공급자 키를 브라우저에 전달하지 않음
서비스 API로그인, tenant·user 확인, 작업·결과 소유권, 제한·감사허용된 실행·상태·중단 기능만 어댑터로 호출
작업 관리자영속 대기열, 공정한 배정, 임대·하트비트, 재시작 복구서비스 작업 ID와 내부 run ID·워커 매핑 관리
Hermes 실행 환경질문 해석·검색 계획·허용 도구 호출·답변 초안제품의 계정·요금·공유 정책을 대신하지 않음
저장소관계형 DB의 작업·권한·이벤트·사용량, 필요한 파일의 객체 저장소브라우저가 Hermes 내부 상태 DB를 직접 조회하지 않음

처음에는 익숙한 프론트엔드·백엔드 기술과 관계형 DB의 영속 작업 큐로 시작할 수 있습니다. 트래픽이 늘면 큐·워커를 분리하고 수평 확장합니다. 배포 플랫폼을 먼저 복잡하게 만들기보다 격리·작업 복구·비용 측정부터 검증합니다.

가이드 배포와 서비스 운영을 구분하세요.

현재 GitHub Pages에는 이 설계 문서를 게시합니다. 실제 제품은 인증 가능한 서비스 API·DB·워커를 별도로 배포해야 합니다. 서비스 UI와 API는 가능하면 같은 출처로 제공하고, 분리한다면 인증 쿠키·CSRF·CORS 정책을 함께 정합니다.

여러 사용자를 안전하게 분리하기

초기 기본안은 사용자별 실행 컨테이너와 전용 저장 공간입니다. 조직 단위 공유가 필요한 경우에만 명시적인 공유 워크스페이스를 추가합니다. 이 선택은 서로 다른 사용자의 데이터와 실행 자원을 분리하기 위한 설계 제안입니다.

Hermes 프로필 문서는 프로필이 상태 디렉터리를 나누지만 파일시스템 샌드박스를 제공하지 않는다고 설명합니다. 공식 Docker 문서의 단일 컨테이너·다중 프로필 운영은 같은 운영 주체의 여러 에이전트에 유용하지만, 이 서비스에는 사용자별 자원·네트워크·자격 증명 분리가 필요하므로 더 강한 경계를 제안합니다.

격리해야 할 대상
경계초기 설계검증할 실패 사례
데이터 접근서버가 로그인 세션에서 tenant·user를 결정. 모든 조회·이벤트·취소·삭제에 소유권 확인다른 사용자의 작업 ID·출처 ID·파일 ID로 교체
실행 상태사용자마다 전용 Hermes home·세션·메모리·캐시·작업 공간·브라우저 상태A의 대화·쿠키·파일이 B의 검색에 섞이는지 확인
프로세스·자원전체 Hermes 프로세스와 사용하는 브라우저를 경계 안에 배치. CPU·메모리·시간 제한terminal 도구만 Docker로 보내고 나머지는 호스트에서 실행되는 구성을 피함
자격 증명사용자용 서비스 로그인과 내부 Hermes 키를 분리. 워커에는 필요한 최소 키만 전달프로필·worker 경로를 브라우저가 선택하거나 키가 응답·로그로 새는지 확인
권한 철회비활성 계정의 신규 작업 차단. 기존 스트림도 철회 신호로 종료하고 재연결·다운로드 시 재검사로그아웃·회원 해제 후 열려 있던 스트림이나 링크가 계속 노출되는지 확인

실행 프로세스는 비루트 사용자로 운영하고 필요한 권한·쓰기 볼륨만 허용합니다. 호스트의 전체 홈이나 Docker 소켓을 에이전트 컨테이너에 마운트하지 않으며, 워커를 배정하는 관리 계층을 에이전트의 실행 권한과 분리합니다. 사용자 수만큼 실행 환경을 항상 켜 둘 필요는 없습니다. 스케줄러가 필요한 사용자 환경을 시작하고 유휴 환경을 정지하되, 상태 볼륨은 사용자별로 유지합니다. 이 방식은 공유 프로세스보다 자원을 더 쓰므로 파일럿에서 메모리·시작 지연을 측정하고, 동시 활성 워커 수도 제한합니다. 하나의 상태 볼륨을 여러 사용자 컨테이너에 공동 마운트하지 않습니다. 같은 사용자 실행 환경도 한 시점에는 하나의 소유자만 제어하도록 작업 임대와 fencing token을 둡니다. 초기에는 사용자당 한 작업을 실행하고, 이후 병렬화 시 상태 접근 규칙을 다시 설계합니다.

대화 ID, X-Hermes-Session-Key, CORS 설정은 사용자 인증·소유권 검사와 별개입니다. 서버가 생성한 내부 ID와 라우팅만 사용하고, 사용자가 보낸 프로필명·내부 헤더·공급자·도구 설정을 그대로 전달하지 않습니다. 객체별 접근 검사의 근거는 OWASP BOLA 안내를 참고하세요.

검색 품질과 근거를 설계하기

기본 파이프라인은 질문 구체화 → 검색 → 원문 추출 → 근거 정리 → 답변 생성 → 근거 검증입니다. 검색 결과의 제목이나 요약만으로 답하지 말고, 실제 확인한 자료를 근거 저장소에 기록합니다.

단계별 요구사항
단계동작기록·검증
범위 설정주제·목적·기간·언어·허용 출처를 확정모호한 날짜·대상은 추가 질문. 검색 조건 버전 기록
검색·원문 확인허용된 검색 도구와 추출 도구로 공개 자료 조회source_id, 실제 URL, 제목, 발행일 또는 미상, 조회 시각
근거 정리주장과 연결할 최소 발췌·문단 식별자·콘텐츠 해시 저장중복·재인용 출처를 구분. 저장은 자료 이용 조건과 보존 정책 범위로 제한
답변 구성요약·비교·상충 정보·한계와 주장별 source_id를 생성모델이 새로 만들어 낸 URL을 근거 목록에 추가하지 않음
검증응답 스키마, source_id 존재, 인용 위치·발췌 일치 검사기계 검사는 주장 진실성의 보장이 아님. 평가셋과 표본 검수 병행

Hermes의 도구 참조에는 web_search와 web_extract가 있습니다. 어떤 검색·추출 공급자를 사용할지는 별도 선택이며, 해당 API의 인증·쿼터·보존 조건을 운영 설정에 포함해야 합니다.

출처 카드가 자동으로 완성된다고 가정하지 마세요.

도구 호출에서 얻은 근거를 수집하고, 주장과 출처 ID를 연결하는 어댑터·검증 로직을 직접 구현해야 합니다. 링크가 열리는 것과 주장을 뒷받침하는 것은 다릅니다. 확인 불가·접근 실패·출처 간 충돌을 결과에 드러내세요.

내부 문서 검색을 추가할 때는 문서 ACL을 검색 전 필터와 결과 제공 양쪽에 적용하고, 캐시·색인에도 조직·문서 권한·버전 범위를 포함합니다. 개인 자료에서 얻은 내용을 공용 메모리나 공용 캐시에 재사용하지 않습니다.

작업 상태·취소·장애 복구

요청 처리와 긴 조사를 분리합니다. DB에 작업과 이벤트를 기록하고, 사용자별 순서와 전체 동시 작업 수를 제어하는 스케줄러가 워커를 배정합니다.

대기 queued→실행 running→완료 succeeded / 실패 failed
  • 중단: queued 작업은 배정 전 취소합니다. running 작업은 stopping 상태에서 내부 stop 요청 후 실제 종료를 확인해 cancelled로 전환합니다. 이미 발생한 모델·검색 사용료가 사라지는 것은 아닙니다.
  • 중복·재시도: 로그인 주체·요청 내용·Idempotency-Key를 연결해 중복 작업 생성을 막습니다. 내부 실행에도 같은 의미의 키를 유지합니다. 같은 키에 다른 내용이면 충돌로 처리합니다.
  • 연결 끊김: 브라우저가 닫혀도 작업은 서버에 남습니다. 다시 연결하면 저장된 이벤트와 현재 상태를 조회합니다.
  • 워커 장애: 임대 만료만 보고 같은 작업을 무조건 재실행하지 않습니다. 기존 실행이 살아 있는지 확인하고, 결과가 불명확하면 recovery_required로 표시해 재조정합니다.
  • 시간 초과: 중단 요청·도구 타임아웃·격리 환경 종료를 순서대로 수행합니다. 실행이 종료된 뒤 timed_out을 확정하고, 늦게 온 이벤트가 상태를 되돌리지 않도록 세대 번호로 걸러냅니다.

Hermes의 중단·재시작·unknown 상태 동작은 버전과 실행 모드에 따라 확인해야 합니다. 서비스 상태와 내부 상태의 매핑을 계약 테스트로 고정하고, “중단 요청 성공”과 “실제 중단 완료”를 구분합니다.

보존 기간은 출시 전에 확정할 결정입니다.

예를 들어 결과·이력은 30일, 원문 임시 캐시는 24시간처럼 목적별로 정할 수 있습니다. 이 수치는 정책 예시이며 법적 보장이나 이미 적용된 설정이 아닙니다. 삭제 요청의 접근 차단 시점, 활성 저장소 정리 기한, 백업에서 만료되는 시점도 따로 정하세요.

기본적으로 사용자를 넘나드는 장기 기억은 사용하지 않습니다. 개인 메모리를 제공한다면 범위·보존·삭제 기능을 별도로 정의하고, 조직 공유 기억은 명시적인 공유 데이터만 대상으로 합니다.

모델·검색 API와 원문 제공자의 서비스 이용 조건, 계정 사용 방식, 데이터 처리 정책을 운영자가 확인합니다. 개인 설치에서 사용하던 로그인 자격을 모든 고객이 공유하는 서비스 자격으로 자동 재사용하지 말고, 서비스 운영에 맞는 인증·과금 방식을 선택하세요.

릴리스마다 Hermes 이미지·모델·프롬프트·도구 정책·응답 스키마 버전을 기록합니다. 버전 변경은 근거 품질·격리·취소·비용 회귀 검사를 통과한 뒤 반영하고, DB·권한 데이터의 백업 복구도 시험합니다.

3 · 팀 업무 확장권한 있는 내부 문서, 후속 조사, 내보내기·명시적 공유검색·캐시·인용·다운로드에서 문서 권한 철회와 삭제가 반영됨
4 · 공개 서비스가입·조직 관리, 과금 정책, 확장·복구·고객 지원예상 피크 부하·장애 복구·사용 조건·운영 책임을 확인한 뒤 공개 범위 결정

출시 전 반드시 통과할 시나리오

  • 사용자 A가 B의 작업·SSE·출처·다운로드·취소 경로를 호출해도 데이터나 제어 권한을 얻지 못합니다.
  • 검색 문서에 “비밀을 보내라” 같은 지시를 넣은 평가 사례에서, 허용 목록 밖 도구·네트워크 호출이 실제로 거부되고 시험용 비밀이 유출되지 않는지 확인합니다.
  • 동일 생성 요청을 반복해도 서비스 작업·사용량 원장을 중복 생성하지 않습니다. 공급자 측 실행 여부가 불명확한 요청은 자동 재실행하지 않고 상태와 비용의 불확실성을 표시합니다.
  • 브라우저 재연결, 워커 재시작, 중단과 완료의 경합에서 상태와 사용량 기록이 일관됩니다.
  • 캐시·메모리·브라우저 상태를 포함한 사용자 격리와 계정 비활성화·자료 삭제를 확인합니다.
  • 사실·최신성·인용 정확도·불확실성 표기를 사람 평가로 확인합니다. 합격 기준은 평가 전에 정하고 근거가 없는 질문도 포함합니다.

처음부터 모든 기능을 만들기보다 공개 자료 탐색 + 근거 확인 + 개인 이력이 유용하고 통제 가능한지 검증합니다. 로그인·격리·비용 제어는 사용자 수가 늘어난 뒤에 붙이는 기능으로 미루지 않습니다.

공식 기능과 설계 제안의 근거

Hermes 기능 설명은 아래 공식 자료를 확인했습니다. 사용자별 워커, 자체 API 경로, 초기 한도와 개발 순서는 이 서비스에 맞춰 제안한 설계이며 Hermes가 그대로 제공하는 완성형 서비스 구성이 아닙니다.

  • Hermes API Server — capability, 실행·이벤트·중단, 인증
  • Hermes Profiles — 상태 분리와 샌드박스의 차이
  • Hermes Docker Setup — 실행·네트워크·자원 분리
  • Hermes Tools & Toolsets — 플랫폼별 도구 설정
  • Hermes Built-in Tools — 검색·추출 기능
  • Hermes Security — 도구 실행과 승인 정책
  • OWASP — 객체별 접근 권한 검사
  • OWASP — 프롬프트 주입 방어
  • OWASP — 서버 측 URL 요청 보호

실제 구현 시에는 배포한 Hermes 릴리스와 capability 응답을 기준으로 계약을 확인하세요. 여기에는 서비스 구현·운영 부하 시험·실사용 계정 연결 결과가 포함되어 있지 않습니다.
